# 论文 官方实现 本地代码一致性审计

## 定义本轮复现目标

先确认用户要核查的是：
- 论文方法与官方实现的忠实复现；
- 保持核心方法的环境移植；
- 同一数据协议下的替代实现；
- 在原方法上加入的自定义改进。

这几类可以各有价值，但名称不能互换。若用户说“复现”，默认先查忠实程度，而不是自行简化后宣称复现成功。

## 建立实际可复查的来源

记录论文及补充材料版本，官方仓库来源与 commit/tag，本地入口、调用链、有效配置，以及相关结果目录。读取入口实际生效参数，不能只依赖 README 默认值。

对已有结果核对运行配置、权重、日志和代码指纹。若没有指纹，明确“无法证明这份结果由当前代码生成”，不凭同目录位置假定对应。

## 差异表

| 环节 | 论文位置与要求 | 官方代码位置与行为 | 本地位置与行为 | 判定 | 可能影响 | 验证动作 |
|---|---|---|---|---|---|---|

判定使用具体类别：
- 已核对一致：仅限列出的环节和版本。
- 可解释的工程差异：需要说明为何预计不改变方法，以及已有何种验证。
- 会改变科学比较的差异：例如标签、划分、损失、上下文或模型选择规则变化。
- 新增方法：例如自定义门控、重置、筛选规则；不得归给原作者。
- 原文与官方实现不一致：并列证据，暂不替作者裁决。
- 无法核实：来源、配置、代码或日志缺失。

“可能影响”是机制分析，不是已经证明的性能原因。不要仅凭指标低就给某个差异定罪。

## 核查顺序

优先影响实验含义的部分，再看局部实现细节；用户指定模块时聚焦该模块。

1. 数据与标签：通道、采样率、滤波、归一化、窗口、时间对齐、缺失处理、评价掩码。
2. 划分与模型选择：人员/会话隔离、验证指标、早停、阈值选择、测试是否参与调参。
3. 模型：输入轴、结构、输出分布、激活、状态、参数共享、论文模块是否被删改。
4. 训练：损失及权重、优化器、学习率、增强、训练预算、初始化、预训练权重和随机性。
5. 推断：eval/train 状态、dropout、批次边界、状态重置、归一化、后处理及未来信息。
6. 指标：单位、宏/微平均、逐人等权或逐窗口汇总、阈值、排除项与不确定性单位。

## 有比例地验证

从能区分假设的最小检查开始：
- 用同一短输入比较官方与本地中间输出，事先说明数值容差和随机性。
- 对索引错位用可手算样本追踪；对递推比较连续处理与分批处理的状态。
- 对损失或概率归一化用小输入核对数学行为。
- 对数据协议差异先重算共同有效样本上的指标，而非重新训练全模型。

合成输入检查通过只能说明被检查的逻辑成立，不能证明真实数据性能。数值相同也只能覆盖已检查的路径。不要为可逆文字编辑或无关实现细节编写镜像测试。

## 修改代码时

用户要求修复时先给出具体改动依据与受影响环节，不必重复索要已给授权。尽量一次只改变能够单独解释的一项因素；确有耦合时说明不能分离的原因。

保留旧配置与结果，为修正版使用新的运行标识。记录改动前后，执行与差异相关的检查。需要 Python 时使用 uv 虚拟环境与 uv pip。

未经相同划分和评价口径复核，不把新旧指标差异都归于修复。大规模训练不是默认验证动作。

## 典型误区示例

以下是审计提示，使用时仍需检查当前文件：
- 窗口网络已有时间上下文，即使去掉显式跟踪，也不能称为“完全没有历史信息”。
- 前向跟踪不使用未来概率，不保证前端预处理没有用未来数据。
- 自定义预测分歧重置属于额外方法，不应写成原论文组件。
- 适配的注意力结构与原论文方程尚未对齐时，不能称为官方精确复现。
- 同一验证人员用于选最佳 epoch，不能把最佳验证得分当独立测试性能。

## 审计结尾

说明已核查环节、最重要差异、哪些差异可能改变结论、尚缺什么，以及下一项最小验证。不要在未做完整核查时使用“完全一致”“所有问题已排除”。
